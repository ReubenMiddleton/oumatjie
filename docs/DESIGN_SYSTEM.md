# Design system

This is the single source of truth for Oumatjie's visual language: the design tokens (color,
type, shape, spacing, motion, haptics), the shared components built on them, and the reasoning
behind each. It exists for the same reason a shared Angular component library or a design-token
package does in a larger codebase — so "what should this look like" has one answer, defined in
one place, rather than each screen quietly reinventing its own card shape or spacing value.
`docs/PRODUCT_PRINCIPLES.md` is upstream of this document (it says *who* the app is for and what
that demands); this document is about *how* those demands are expressed consistently in code.

Read this before adding any new screen or component. If a new screen seems to need a color,
shape, spacing value, or interactive pattern that isn't listed here, that's worth pausing on —
either an existing token/component actually covers it, or this document is genuinely missing
something and should grow to include it, rather than the new screen inventing a one-off.

## Why a written design system, not just consistent-looking code

Two screens that happen to use similar-looking cards today can quietly drift apart over time —
someone changes a corner radius in one file during an unrelated fix, and now there are two card
shapes with no record of whether that was deliberate. A written token file plus shared,
documented components makes the intended look explicit and gives future changes one place to
happen: change `OumatjieShapes` in `ui/theme/Theme.kt` and every card in the app picks it up;
change `OumatjieInfoCard` in `ui/components/GranifyComponents.kt` and every banner, note, and
result card in the app changes with it. This is the same principle behind an Angular shared
component module (or a React/Vue design-system package): presentational components that own a
visual pattern once, take typed inputs, and get reused everywhere that pattern is needed, rather
than each feature re-declaring its own version of "the card look."

## Color

Defined in `ui/theme/Theme.kt`'s `OumatjieColors` (a Material3 `lightColorScheme`). Every role
Compose actually resolves was hand-set and checked against WCAG contrast math — never left to
Material3's baseline neutral-gray defaults, which don't match this palette and were never
contrast-checked for it (see `docs/DECISIONS.md`, "Color palette and contrast"). No role here was
generated by pasting a brand color into a Material seed-color tool; each was chosen and checked
individually, which is also why the palette doesn't read as a generic Material "seeded from one
hex" scheme (see "Avoiding a generic/AI-generated look" below).

| Role | Hex | Used for |
|---|---|---|
| `primary` | `#174E3A` | A deep, warm green — the Hero button, the wordmark on the sign-in screen. Deliberately not a Material-blue or a tech-startup purple/indigo. |
| `onPrimary` | `#FFFFFF` | Text/icons on `primary`. |
| `primaryContainer` | `#D7F4E5` | Unread mail cards in the inbox. |
| `onPrimaryContainer` | `#082C20` | Text on `primaryContainer`. |
| `secondaryContainer` | `#FFE7B3` | A warm amber — "worth a second look" surfaces: the first-contact note, a scam-check result, an attachment card. Calm, not alarming (`docs/PRODUCT_PRINCIPLES.md`: "calm, factual warnings"). |
| `onSecondaryContainer` | `#392D00` | Text on `secondaryContainer`. |
| `background` / `surface` | `#FFFDF7` | An off-white, not stark `#FFFFFFFF` — softer under the amount of reading this app expects. |
| `onBackground` / `onSurface` | `#1C1B18` | Body text. Warm near-black, not pure `#000000`, to match the warm background. |
| `surfaceVariant` | `#E8E2D6` | Read (already-opened) mail cards; neutral result cards (a message summary). |
| `onSurfaceVariant` | `#49443A` | Text on `surfaceVariant`; also used for de-emphasized inline text (an "add a key to enable this" hint). |
| `error` | `#9B1C1C` | Reserved for Material3's own internal use (form-field error indication); not directly used in hand-written screens today. |
| `errorContainer` | `#FBE4E1` | Something failed and blocks the user — a sign-in failure, a load error. |
| `onErrorContainer` | `#5A1414` | Text on `errorContainer`. |
| `outline` | `#756C5C` | Dividers, low-emphasis borders. |

Every text-bearing pair above clears WCAG AAA (7:1); `outline`, which is non-text, clears the 3:1
non-text threshold at 5.09:1. If a new screen needs a color role not listed here, add it to
`OumatjieColors` with the same contrast bar, not as a one-off hardcoded `Color(0x...)` in a
composable.

## Typography

Every Material3 `Typography` style — all ~15, not just the ones with a custom size override — is
routed through Atkinson Hyperlegible, a typeface designed by the Braille Institute of America
specifically for low-vision and aging readers, with deliberately distinct letterforms for
commonly-confused characters (`I`/`l`/`1`, `0`/`O`). See `ui/theme/Theme.kt`'s
`OumatjieTypography` and `docs/DECISIONS.md`, "Atkinson Hyperlegible wired into every Typography
style." Seven styles also carry a larger custom size than Material3's default — `bodyLarge` at
20sp is the main body-text size used throughout the app, noticeably larger than the 16sp a
generic Material app would ship.

Never hardcode a font size or family in a composable. Use `MaterialTheme.typography.*` and let a
theme change propagate automatically — this is also what makes the in-app text-size setting
(`data/settings/TextScale.kt`) work without every screen needing to know about it.

## Shape

A deliberate **two-radius system**, defined once in `ui/theme/Theme.kt`'s `OumatjieShapes` and
consumed everywhere via `MaterialTheme.shapes.medium` / `.large` — never a hardcoded
`RoundedCornerShape(16.dp)` sprinkled into an individual composable. Before 2026-08-24 the app
had exactly that: `16.dp` and `20.dp` values hand-typed into five different files with no shared
definition, which is both a maintenance hazard (change one, forget the others) and one of the
recognizable tells of an unstyled, AI-scaffolded UI — a *uniform*, untouched corner radius (or an
arbitrary, undocumented mix of them) rather than a considered, named scale.

| Token | Radius | Meaning | Used by |
|---|---|---|---|
| `shapes.medium` | 16dp | **Informational surfaces** — a banner, a note, a result the user didn't directly create. | `OumatjieInfoCard` (`ui/components/GranifyComponents.kt`) and everything built on it: the first-contact note, the scam-check banner, a message summary, an attachment card, inline error cards on the sign-in and message screens. |
| `shapes.large` / `shapes.extraLarge` | 24dp | **Primary, tappable content surfaces** — something the user reaches for. | `MailCard` in `ui/mail/MailScreens.kt` (each row in the inbox); `AlertDialog` (`ConfirmationDialog`), via Material3's own default wiring of dialogs to `shapes.extraLarge`. |
| `shapes.extraSmall` / `.small` | Material3 defaults (unchanged) | Small, incidental elements. | Not directly used by hand-written screens today; left at Material3's defaults deliberately, since a signature treatment on a menu or chip would add visual noise without a legibility payoff for this audience. |

Adding a third radius should be rare and deliberate — the whole point is that "which shape does
this get" has an obvious, memorable answer (informational vs. primary-content), not a spectrum of
options to choose between per screen.

## Spacing

Not (yet) formalized as named Dp constants — every screen currently writes `Modifier.padding(N.dp)`
directly — but a real, if organic, scale is already in consistent use across `ui/`, and any new
screen should draw from it rather than picking an arbitrary value:

`4dp, 8dp, 10dp, 12dp, 16dp, 18dp, 20dp, 24dp, 28dp, 32dp`

In practice: `20dp` is the standard screen-edge and card-internal padding (`LazyColumn`'s
`contentPadding`, `OumatjieInfoCard`'s internal `Column` padding); `8dp`–`12dp` is the standard
gap between stacked elements within a card or section (`Arrangement.spacedBy`); `24dp`+ marks a
clear section break (the gap before the sign-in screen's error card, `MessageScreen`'s top-level
`spacedBy(18.dp)`). A future pass could promote this into a real `object OumatjieSpacing { val sm
= 8.dp; ... }` token file the way `OumatjieShapes` now exists for shape — worth doing once a
second or third screen makes the inconsistency between "should this gap be 16 or 20" a real
question, rather than speculatively now.

## Shared components

Everything below lives in `ui/components/GranifyComponents.kt` (the file itself keeps its
pre-rename basename — see `docs/DECISIONS.md`'s rename entry — but every symbol inside it is
`Oumatjie`-prefixed) unless noted otherwise. Treat this the way you'd read a shared Angular
module's list of exported components: what it's for, what it takes as input, when to reach for
it instead of writing a one-off.

| Component | Purpose | Key parameters |
|---|---|---|
| `OumatjieHeroButton` | The one primary forward-moving action on a screen (~80dp). "Continue with Google," "Done reading," "Open document." One per screen — a second Hero button undermines the hierarchy this exists to create. | `label`, `onClick`, `enabled` |
| `OumatjieButton` / `OumatjieSecondaryButton` | Standard-tier actions (64dp) — real but not the single primary choice. Filled vs. outlined for visual sub-hierarchy (e.g. a destructive action placed below the primary one). | same |
| `OumatjieTertiaryButton` | Low-stakes, always-available navigation (~56dp, text style) — "Back to your mail," "Settings," a dialog's "Cancel." | same |
| `LoadingScreen` | Full-screen centered spinner plus a message. Use for "this whole screen isn't ready yet," not for a small in-place loading state (those use a `Row` with a small `CircularProgressIndicator`, e.g. `ScamCheckBanner`'s "Checking this message…"). | `message` |
| `ErrorScreen` | Full-screen "there's nothing else to show" failure — the inbox failed to load entirely. Distinct from `OumatjieInfoCard(tone = Problem)`, which is for a failure with context still on screen (see below). | `message`, `onTryAgain` |
| `ConfirmationDialog` | A plain-language confirmation before a hard-to-undo action, explaining what happens next (`docs/PRODUCT_PRINCIPLES.md`: destructive actions are explained and reversible where possible). Never a bare "Are you sure?". | `title`, `explanation`, `confirmLabel`, `onConfirm`, `onDismiss` |
| `OumatjieInfoCard` | The shared informational-surface wrapper — see "Shape" above. Owns the shape/color/padding; callers supply their own content (title, body, an inline action, a loading row) via a trailing `@Composable ColumnScope.() -> Unit` lambda, the same content-projection idea as an Angular component's `<ng-content>`. | `tone` (`InfoCardTone.Neutral` / `.Highlight` / `.Problem`), `contentSpacing`, `content` |

### `OumatjieInfoCard` in practice

Before 2026-08-24, five separate composables across three files each hand-declared their own
`Card` + `RoundedCornerShape` + `CardDefaults.cardColors` + padded `Column` for what was
visually the same surface: the first-contact note, the scam-check "worth a closer look" card, a
message summary result, an attachment's details, and two different inline error cards (sign-in
failure, message-load failure). They'd already drifted slightly (some used a hardcoded
`RoundedCornerShape(16.dp)`, one used no explicit shape at all and fell back to Material3's
un-themed default) despite being the same design intent. All six now build on `OumatjieInfoCard`
with one of three `InfoCardTone` values:

- **`Neutral`** (`surfaceVariant`) — routine information the user asked for. A message summary.
- **`Highlight`** (`secondaryContainer`) — worth a second look, but calm, not alarming. A new
  sender, a scam-check finding, an attachment's details.
- **`Problem`** (`errorContainer`) — something genuinely failed or blocks progress. A sign-in
  failure, a message-load error.

If a new screen needs a colored informational card, it should almost always be
`OumatjieInfoCard` with the tone that matches its intent — not a new hand-rolled `Card`. If none
of the three tones fit, that's a real signal this document (and the enum) needs to grow, the same
way a genuinely new variant gets added to a shared Angular component's `@Input` rather than
worked around by a one-off template downstream.

## Motion

A single global rule, not per-screen tuning: `OumatjieNavHost` (`ui/navigation/GranifyNavHost.kt`)
overrides Navigation Compose's default slide+fade transition with a plain 150ms crossfade,
applied once via `NavHost`'s own transition parameters. Inbox list items additionally get a
short, gentle fade on entrance/exit (`Modifier.animateItem`, 200ms in / 150ms out, a `tween` not
a spring — chosen to match the same plain, non-bouncy character as the crossfade). Both are
deliberately restrained: `docs/PRODUCT_PRINCIPLES.md` calls for reduced motion, and a bouncy
spring or a large slide/parallax effect reads as "trying to look modern" rather than "calm and
legible." Don't add a new transition style without checking this section first — one motion
language, used everywhere, is the goal.

## Haptics

Every button tier fires a light haptic tick on tap (`LocalHapticFeedback.performHapticFeedback`):
`HapticFeedbackType.Confirm` for `OumatjieHeroButton` and a dialog's confirm action (these
represent committing to something), `HapticFeedbackType.VirtualKey` for the other tiers (a
lighter tick for lower-stakes taps). This exists because roughly a third of adults 65–74 have
some hearing loss (`docs/ROADMAP.md`'s motion/haptics research) — a tap-back vibration confirms
the tap happened without depending on hearing a sound cue. Any new interactive element that
commits to something (not just navigates) should fire `Confirm`; anything else that's tappable
should fire `VirtualKey`. Silence (no haptic at all) should be rare and deliberate, not an
oversight.

**Sound is deliberately not used for feedback anywhere in the app — a considered "not now," not
an oversight.** See `docs/DECISIONS.md`'s "Sound as a feedback channel — evaluated, not built"
entry for the research and reasoning. Haptics plus a visible text confirmation (a snackbar, an
inline banner) already cover every feedback moment the app has; if sound is ever added, it must
never be the only channel carrying information (WCAG-aligned with this app's existing
"no color-only signals" rule), must be off by default, and must explicitly check
`AudioManager.getRingerMode()` before playing — Android's UI-sound stream types do not
automatically respect the device's silent/vibrate setting, so an app that plays a sound without
checking this can ring out loud on a phone its owner deliberately silenced.

## Iconography and illustration

The app icon (`res/drawable/ic_launcher_*.xml`) is hand-written vector XML — a dark-green
background plus a stroke-only, line-art envelope glyph, not a generated PNG or a stock icon-pack
asset (`docs/DECISIONS.md`, "App icon is hand-written vector XML"). It's a first real pass, not a
placeholder, but also not a commissioned mark — if real branding/a logo is commissioned later,
this is the file to replace outright, not redesign around.

No other illustration exists in the app yet (no empty-state artwork, no onboarding graphics). If
one is added — an empty-inbox state is the obvious first candidate — keep it in the same
register as the launcher icon: simple, two-color, line-art, not a busy multi-color stock
illustration. A detailed, saturated stock-style illustration next to this app's otherwise
restrained, typography-and-color-led screens would look pasted-in rather than designed together.

## Avoiding a generic/AI-generated look

This section records the specific, researched reasoning behind choices elsewhere in this
document, so a future change doesn't accidentally undo them by reaching for a "safer," more
generic default. The recognizable tells of an unstyled or AI-scaffolded interface, and this
app's specific countermeasure for each:

- **A single uniform corner radius everywhere** (or Material3's own untouched default) reads as
  "never actually decided on a shape language." Countered by the two-radius system above, used
  consistently rather than per-composable ad hoc values.
- **An untouched Material/Tailwind seed palette** — especially the indigo/violet/purple gradient
  combination that shows up by default in a huge number of scaffolded apps and dashboards —
  reads as "picked a starter theme and shipped it." Countered by `OumatjieColors`: a specific,
  hand-checked warm green/amber/off-white palette with no seed-color generator in its history,
  chosen for tone (calm, warm, unhurried) as much as for contrast math.
- **Generic system-default type at a generic size** reads as "text, rather than a considered
  typographic voice." Countered by Atkinson Hyperlegible at a larger-than-default body size,
  applied to every style rather than a partial pass.
- **Decorative elements with no functional reason to exist** — gradient blobs, abstract shapes
  scattered behind content — read as filler. This app has none, deliberately; every colored
  surface (`OumatjieInfoCard`'s tones, `MailCard`'s unread/read distinction) carries real
  information rather than decorating the page.
- **A generic ripple/fade on everything, or conversely no motion at all**, both read as
  unconsidered. Countered by the specific, restrained motion language above (a 150ms crossfade,
  a gentle list-item fade) plus haptic feedback layered on top of the visual response — a
  combination a purely visual, unstyled scaffold wouldn't have reason to include.
- **A busy, multi-color stock illustration dropped into an otherwise plain interface** reads as
  "borrowed asset," not "designed for this app." Covered under "Iconography and illustration"
  above.

None of this is about adding visual complexity for its own sake — the audience this app is built
for (`docs/PRODUCT_PRINCIPLES.md`) benefits from restraint, not decoration. The goal is that the
restraint reads as a deliberate, considered choice (a specific palette, a specific shape
language, a specific typographic voice, used consistently) rather than as the absence of one.
